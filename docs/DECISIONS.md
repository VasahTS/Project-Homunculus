## D-001 — World state is attached to each message (2026-10-23)
State is stored as deltas per message and rebuilt along the message path. Swipes, branches and going back always show the right state. Pinned values apply on every branch.
Reason: Daniel swipes, branches and rewinds often. Costs and their fixes: store only deltas (disk); setting to run agents only when the story continues from a swipe (tokens); pins for manual edits that must survive branches.
Implemented: `packages/core/src/state.ts`, tests in `packages/core/test/state.test.ts`.

## D-002 — Tauri, no Electron fallback (2026-10-23)
Daniel already has Tauri installed and another Rust + Tauri app working.

## D-003 — The core is TypeScript; Rust only for small native parts (2026-10-23)
One language for almost everything: fewer AI mistakes and fewer tokens. Rust is used for the API-key vault, file access, backups and, later, heavy work (local embeddings). The core stays isolated so a piece can move to Rust later.

## D-008 — SQLite through a tiny SqlDriver; rich objects stored as validated JSON (2026-10-23)
`SqlStore` (core) talks to `SqlDriver` (`execute`/`select`, `?` placeholders). Drivers: Tauri SQL plugin (desktop, file `homunculus.db` in the app config folder) and sql.js (tests + browser preview). The same SQL code runs everywhere, so tests cover the real queries.
Characters and sessions are stored as JSON validated by Zod on read: adding a field needs no migration. Messages, branches and state have real columns (queried often). Migrations are numbered and never edited after shipping; the desktop app backs up `homunculus.db` to `backups/` before upgrading an existing database (Rust command `backup_database`).

## D-009 — Offline test AI + API key in memory only (for now) (2026-10-23)
An "Offline test AI" provider lets anyone try the app and lets e2e tests run without a key. The real provider is `@homunculus/provider-openai` (OpenRouter by default, any OpenAI-compatible address). The API key is kept only while the app is open until the secure vault (Rust, OS keychain) is built — next step. Connection settings except the key are remembered locally.

## D-011 — API keys live in the OS keychain (2026-10-23)
Rust commands `secret_get/set/delete` (crate `keyring`, Windows Credential Manager on Daniel's PC, service "Homunculus"). One key per provider + address (`api-key:<provider>:<address>`). Keys never go to the database, files or localStorage. The key saves when the user leaves the key box; "Forget key" deletes it. Browser preview uses a memory-only store. Supersedes the "memory only" part of D-009.

## D-012 — SillyTavern cards: lossless border (2026-10-23)
`@homunculus/st-cards` (module) imports PNG (`ccv3` preferred, falls back to `chara`) and JSON cards V1/V2/V3, and exports PNG (both `chara` V2 and `ccv3` V3 chunks) and JSON (same version as imported). The whole original card is kept in `character.original`; export starts from it and overwrites only the fields Homunculus edits, so embedded lorebooks, extensions and tool-specific fields survive. Pure TypeScript PNG reader/writer (no image library). Characters without an image export with a plain placeholder PNG.
Avatars live in their own table as PNG base64 (migration 2); any picked image is converted to PNG in the UI. Exports are saved to the Downloads folder by the Rust command `save_download` (never overwrites: "name (2).png").
Macros: messages are stored raw; `{{char}}`/`{{user}}`/`<BOT>`/`<USER>` are filled in for display and in the prompt (user = "User" until personas exist).

## D-015 — Slice 0 done: the foundation follows the blueprint (2026-10-27)
Daniel approved BLUEPRINT v2 and asked to "work from big to small". Implemented in one pass, old data still loads:
- **Schemas split by area** (`common`, `library`, `setup`, `play`, `agents`, `trackers`, `records`, `legacy`). Sessions saved by v0.0.1 are upgraded on read (`upgradeSession`), so Daniel's database needs no data migration.
- **Layered setup**: `Session.setup` / `Campaign.setup` / Default (`app_settings.defaultSetup`) resolved only by `resolveSetup`. Agents, trackers and companions are all in `setup.agents`.
- **One agent model**: `AgentConfig` (data) for every agent; built-in agents are `config + output schema + run`. Data agents run through executors (`separate` built in; `inline` handled by the turn). Outputs are applied in one place (`AgentRunner.apply`).
- **Ordering**: dependencies first; intercept/rewrite/check one by one by `order`; everything else in parallel by dependency level. A state namespace has one owner (first by order, then id); `lockedForAgents` fields are dropped from agent writes.
- **TurnPipeline** replaces the old `ChatService.generate` internals; `ChatService` keeps the same calls for the UI.
- **Records per message**: `agent_runs` (+ `stale`), `message_revisions`, `agent_notes`, `generation_records` (prompt parts with sources), `state_user_deltas` (user edits win at that message), `state_snapshots` (cache every 50 messages, invalidated by later-or-equal `created_at` in the session).
- **Connections**: per-connection gate (default 4 at a time), optional min interval, fallback only before the first token, Stop everywhere.
- **Reasoning** of thinking models is saved apart (`Message.reasoning`), shown folded in the chat, never sent back.
- Swipes with `trackersOnSwipe = false` skip state agents; continuing from such a swipe runs them first ("catch-up", only for replies recorded as swipes).
- Migration 3 adds the new tables and three nullable message columns; the desktop app backs up the database before it runs (D-008).
Verification: 81 unit tests (was 45) + 17 click tests (was 16), typecheck clean. No Rust changes in this slice.

## D-016 — Proof of concept: trackers are user data, the engine only reads the schema (2026-10-27)
Daniel's rule (2026-10-27): **no tracker with a fixed name or purpose in the code** ("avoid labels like 'emotions tracker'; it must be modular and serve however the user chooses"). So the app ships **no** tracker. The user makes one in the **tracker editor** (name, description, instructions for the AI, how many messages it reads, and fields: text / number / bar / status / list; one value, one per character or one per pair; "only I change it"; "send to the AI"). Ready-made field sets, if they ever exist, come as optional data (import file or Kit), never as code. BLUEPRINT §4.5 updated.
How it is stored: a tracker = an `AgentConfig` (output `state`, trigger turn.after, run mode separate) + a `TrackerSchema`, **same id for both, and that id is the state namespace**, so renaming the tracker or a field never loses saved values (field keys are made once from the label and never change). Switched on per session in the session's setup layer (`setup.agents` add) from the Scene panel; the full setup screen comes in slice 4. Deleting a tracker switches it off in every session; old values stay in old messages.
Engine (`packages/core/src/trackers.ts`, used by the runner): the AI gets the field list + an example answer and reads/writes **character names**; the app stores **character ids**. Answers are cleaned against the schema before saving (see ARCHITECTURE.md); what was left out is logged on the run; an answer where nothing fits is a failed run (the reply is never lost). Values with "send to the AI" go back into the main prompt as a "Current scene" part (source `state:<trackerId>`, visible in the generation record).
Turn change: `onReply` callback (TurnRequest / GenerateOptions) fires when the reply is saved, before "after" agents run, so the chat shows the reply at once and the panel says "updating…" until trackers finish.
UI: Scene panel (right of the chat, can be hidden) drawn only from the schema, values **at the last message on screen** (swipes/branches show their own), edits saved as the user's delta at that message (marked ✎, win over the tracker), run log per message (status, time, model, tokens, what it answered, what it left out, "out of date"), "Run now/Run again". The offline test AI answers any tracker by varying the example answer, so everything works without a key.
Also fixed the same day: the user's sent message vanished from the screen until the AI finished (the list was only redrawn at the end) and the "writing…" bubble blinked away before the final list loaded; swipes now hide the old version while the new one is written; live "is thinking…" reasoning.
Verification: 88 unit tests (was 81) + 24 click tests (was 17), typecheck clean. No Rust changes, no database migration (new data fits the existing tables; `AgentRun.warnings` is optional).

## D-018 — UI direction "I" (Apple HIG over the "Inspector" layout), and a UI that stays modifiable (2026-10-27)
Daniel found the app "painful to look at" and asked to move the UI work earlier. Mockups A–J were made on a design canvas; he chose **I** (the "Inspector" layout H, redone with Apple's Human Interface Guidelines, skill github.com/dickwu/apple-design-skill @914b6a37), "together with H" — H's per-reply **receipt** is kept. Neutral look for now (graphite, verdigris accent `#62B6A4`); Blood & Ink comes later as a theme. His rule: "the UI must always stay modifiable as the app evolves", like the v1 Customize screen (visual profiles, layout, effects, profile tweaks, import/export).
Layout:
- **Two layers**: a functional layer (sidebar, inspector) floats as glass over an opaque content layer (story, library detail). Glass becomes opaque with `prefers-reduced-transparency`.
- **Sidebar, two levels**: Sessions (new session picks the character) and Library (Characters, Trackers; later Personas, Lorebooks, Presets, Agents). Library pages are master-detail (`LibraryPages.tsx`), one shape for every kind.
- **Toolbar**: no bezels, at most three groups (leading / center / trailing). Sidebar and inspector can be hidden; the choice is remembered (localStorage, per viewer).
- **Story**: prose in Literata, UI in the system font; one prominent action (**Send**); Title Case on buttons. Under the last reply, a one-line **receipt** (tokens, time, trackers updated) opens the Reply tab; older replies have "Details".
- **Inspector**: one panel, segmented tabs **Scene** (trackers at the message on screen) · **Prompt** (connection + samplers with slider and number box; empty = model default) · **Reply** (what was sent, by source, with a bar; settings used; agents after the reply with Run Again; what changed, using field labels and names; full prompt). Everything there already came from the per-message records (BLUEPRINT §2.4); nothing new is stored.
Modifiability (how future themes and screens plug in):
- **Tokens** (`apps/desktop/src/theme/tokens.css`) are the only place with colors, radii, fonts, sizes and panel widths. `styles.css` uses tokens only.
- **Appearance profiles** (`theme/themes.ts`): `{ id, name, tokens, layout, effects, tweaks, css? }`, applied by `applyProfile` (sets `data-theme`/`data-layout` on `<html>`, token overrides as CSS variables, optional custom CSS). One built-in today, "Graphite". Profiles are plain data, so import/export and a Customize screen are straightforward later.
- **Stable hooks**: `data-region="app|sidebar|toolbar|story|composer|inspector|library|editor"` for themes and custom CSS; class names are kept stable on purpose.
- **Small kit** (`ui/kit.tsx`): Button (plain/bordered/prominent/destructive), IconButton, Segmented, Switch, Group/Row (Settings-style grouped lists), Icon. New screens are built from it, so a theme changes them all.
Later (not built): the **Customize** screen (profiles, layouts such as a "Control" layout close to G, effects, tweaks, import/export), the native menu bar with every command, Blood & Ink theme, prompt blocks in the Prompt tab (slice 2).
Verification: typecheck clean, 94 unit tests + 29 click tests (3 new: receipt → Reply tab, samplers used by the next reply, hide/show panels kept after reload). No core, Rust or database changes. New dependency: `@fontsource/literata` (font bundled locally, no network).

## D-019 — Slice 1: character versions, personas, history of saves, the Trash (2026-10-28)
Daniel chose to do slice 1 now and refine the UI later; settings and connection profiles come right after (his request, 2026-10-28).
The five questions (BLUEPRINT §13): pieces = Character and Persona (§2.1, variants §2.5) plus two library rules (§2.6: history, Trash); setup layer = the session picks each cast member's version (`CastMember.variantId`) and the persona (`setup.personaId`/`personaVariantId`; the Default layer holds the default persona); turn step = prompt assembly only (step 4); core for data (store, prompt) + module `st-personas` for the SillyTavern border; per message = the generation record now keeps **who** was in the story (`GenerationRecord.who`: persona, persona version, cast versions); failure/undo = nothing is deleted at once (Trash with Undo), every save is a history entry that can be restored.
- **Versions (variants)**: edited in the character/persona editor with a "Version" bar (Main + versions + "New Version"). A version stores only what differs (overrides equal to Main are pruned on save, `pruneOverrides`), so editing Main still reaches fields a version did not change. Each version may have its own picture (avatar key `<id>#<variantId>`); without one it uses Main's. Export writes the version on screen as a normal SillyTavern card (variants never go into cards). A session picks versions in the toolbar's **"who is in this story"** popover, or when it is created (sidebar "+" and "Start Session with Lyra (Modern)"). A deleted version falls back to Main.
- **Personas**: Library → Personas (master-detail like Characters): name, description, picture, versions, **place in the prompt** (with the character / near the end at depth N with a role / not sent — SillyTavern's IN_PROMPT, AT_DEPTH, NONE; its Author's Note positions map to "with the character" with a warning), default persona switch. The first persona created (or imported, preferring SillyTavern's default) becomes the default. `{{user}}` and the user's name in the chat follow the persona (version included); without one it is "User".
- **SillyTavern import** (`packages/st-personas`, `registerPersonaImporter` — importers get all picked files at once): the "Backup" JSON of Persona Management (`personas`, `persona_descriptions`, `default_persona`; format from `public/scripts/personas.js` `onBackupPersonas`) or the whole `settings.json` (`power_user.…`), plus persona images picked together (matched by file name, from `data/default-user/User Avatars`). The ST data (avatar id, title, lorebook link…) is kept in `Persona.original`. Persona lorebooks are reported and kept for slice 3.
- **History** (migration 4, table `item_history`): every save of a character or persona stores the whole item (with its versions); no entry when nothing changed; the first edit of an item saved before history existed also keeps the old version; at most 100 per item. The editor's "History" lists saves (what changed, values) and restores one (restoring is itself a save, so it can be undone). Pictures are not in the history. Other kinds (presets, lorebooks, agents, kits) join when they get editors.
- **Trash** (migration 4, `trashed_at` columns on characters, personas, sessions — outside the JSON, so saving never untrashes): "Move to Trash" replaces delete for sessions, characters and personas, with **Undo** in the notice; Library → Trash restores or deletes forever (two clicks), or empties all. Lists hide trashed items but `get` still finds them, so nothing that points at them breaks. Refused with a plain reason: a character used by a session that is not in the Trash; the default persona; a persona a session picks. Delete forever waits for trashed sessions that still use the item; Empty Trash deletes sessions first. Trackers are still deleted directly (they switch off everywhere) — they join the Trash later.
- Also: `npm test` no longer runs the tests of the downloaded reference projects (`vitest.config.ts` excludes `.refs/`); a flaky click test (status line visible only 0.3 s) now slows the offline tracker down for that test.
Verification: 103 unit tests (was 94) + 35 click tests (was 29), typecheck clean. No Rust changes. Migration 4 runs on first start, after the automatic backup.

The editor's **Browse** button opens a picker: search (every word must match name, id or description), sort by name / cheapest / largest context, "thinking only", Refresh; the list is kept for this run of the app per provider + address. After picking, the model's details show under the field, and reasoning levels the model doesn't accept are greyed out. API Key now comes before Model in the editor.

## D-021 — Slice 2: presets by blocks, macros, context budget, SillyTavern presets, Preview Prompt (2026-10-28)
Next slice in BLUEPRINT §10 order (Daniel: "pode prosseguir para o próximo passo").
The five questions (BLUEPRINT §13): piece = **Preset** (§2.1; table `presets`, migration 6, with history and Trash like personas); setup = `presetId` in every layer (Default in Settings → Defaults, per session in the Prompt tab); turn step = prompt assembly (step 5 of §6); core (`presets.ts`, `macros.ts`) + module `st-presets` (the SillyTavern border); per message = `GenerationRecord.presetId`, `budget` (estimated tokens used, limit, room for the reply, messages left out) and `promptNotes`; failure/undo = nothing is dropped in silence (notes), edits have history, presets go to the Trash.
- **Preset** = ordered **blocks** (text with macros, or a **marker** the app fills: SillyTavern's `charDescription`, `charPersonality`, `scenario`, `personaDescription`, `dialogueExamples`, `chatHistory`, `worldInfoBefore/After` — empty until lorebooks, slice 3 — plus ours `scene` and `agentPrompts`), each with role, on/off, place (in the list, or **inside the chat N messages before the end** with an order), triggers (generation types) and "a card can replace this block"; context size; optional samplers that win over the connection's **for the story only** (agents keep their connection's); formats for marker text; SillyTavern's small texts (before the chat, example-chat marker, prefill; continue/impersonation kept for later); "join system messages" (ST squash). `prompt-v0.ts` is gone.
- **Builder** (`buildPrompt`) follows SillyTavern's Chat Completion assembly where presets depend on it (references in the file header): a card's system prompt replaces the `main` block (`{{original}}` = the block's text), its post-history instructions replace `jailbreak`; depth blocks go into the chat with higher order first, then system/user/assistant; **no Chat History block = no conversation** (as in ST, with a note). Ours: when a preset has no `scene` / `agentPrompts` block, they go right before the chat history **with a note** (BLUEPRINT §5.1). The session's scenario replaces the card's (as in ST).
- **Context budget** (BLUEPRINT §5.2, first version): everything but the chat is fixed; the chat gets the rest of `contextSize − room for the reply` (the reply's max length, else 1024), newest messages first; the last message is always sent (with a note if even it doesn't fit). Token counts are estimates (≈3.6 characters per token) until the service reports real ones. Per-marker caps and priorities (World Info ≤ 25%, etc.) come with lorebooks.
- **Macros** (`expandMacros`, SillyTavern syntax): char, user, description, personality, scenario, persona, mesExamples, model, original, lastMessage/lastUserMessage/lastCharMessage, newline, trim, noop, `//` comments, random (`::` or `,`), **pick** (stable per message, so swipes keep the choice), roll (`1d20`, `2d6+1`), time/date/weekday/isodate/isotime, setvar/getvar/addvar/incvar/decvar (live for one prompt — SillyTavern keeps chat variables; ours persist later with the state), legacy `<BOT>/<USER>`, **`{{state.tracker.field}}`** (ours), and macros from modules (`registerMacro`). Unknown macros stay as written. Not yet: `{{if}}` blocks, outlets, instruct macros.

## D-032 — Branches are paths in the message tree; only their names are saved (2026-10-29)
Daniel: branches "similar to SillyTavern or Marinara; Aventuras' is too limited". Text plan → mockups (canvas "Homunculus 2 — Branches": Main, Tree, Actions) → approved ("pode fazer assim entao"), with option (a) for swipes.
- **Model (`core/branches.ts`, pure):** messages already form a tree and world state is pinned per message (deltas, user deltas, snapshots), so a branch copies nothing — unlike SillyTavern/Marinara, which copy the chat file. `computeBranches(links)`: walking from the root, a child that nobody continued is a *version* (swipe), not a branch; every continued child starts its own path; the newest version ends a path. Each branch has `key` (its first own message), `endId`, `path`, `forkAt`, `own` (the key's subtree: what Delete removes), times. Sorted oldest first; the oldest is "Main". `forkPoints` = messages after which ≥2 branches go different ways (the marker).
- **Names (`nameBranches`):** the `branches` table holds one row per branch, `head_message_id` = the key when first seen. A row matches the oldest unnamed branch whose path holds its head, so names stay put when branches split again or others are deleted; branches without a row get "Main" (oldest) or the next free "Branch N" and are saved once (the UI serializes loads); rows that match nothing are deleted. "Branch from here" names the branch on the next send (the row whose head is the new user message).
- **Store:** `messageLinks`, `messagesOf`, `deleteMessages(sessionId, ids)` (for good: deltas, user deltas, revisions, snapshots, agent runs and notes, generation records, branch rows, messages), `deleteBranch`. `ChatService.copyPathToNewChat(sessionId, endId, title)` = "Make a Separate Chat" (session copy + path messages with their deltas, user deltas and records).
- **UI (`Branches.tsx`, `ChatView.tsx`):** toolbar "⑂ <branch> ▾" list (current first; rename; delete forever with confirm, never the one on screen; Show Tree; Make a Separate Chat); marker "The story splits here · N branches"; message action bar (versions, Copy, Edit, New Version, Branch from here, Hide from the AI = `visibility.ai: "none"`, Details | Delete = the message's subtree, for good, with counts); Tree sheet; sidebar "⑂ N" and story chat card "N branches".
